Most React applications deal with forms. Traditionally, we handle submissions with `onSubmit`.
React 19 added support for passing functions to a form’s `action` prop.
In this post, we’ll compare three approaches: plain `onSubmit`, `action`, and `onSubmit` with `useTransition`.

Throughout this post, we’ll use the following mock subscription API.
It simulates a one-second request and returns an error for `test@example.com`,
or success for any other email. All three form examples below refer to this same `subscribe` function.

```ts
async function subscribe(email: string) {
  await new Promise((resolve) => setTimeout(resolve, 1000));

  if (email === "test@example.com") {
    return {
      success: false as const,
      error: "This email is already subscribed.",
    };
  }

  return { success: true as const };
}
```

## Handling form submissions with `onSubmit`

Let’s start with a newsletter subscription form using `onSubmit`:

```tsx
import { useState } from "react";

export default function NewsletterForm() {
  const [isSubmitting, setIsSubmitting] = useState(false);
  const [error, setError] = useState("");
  const [success, setSuccess] = useState(false);

  async function handleSubmit(event: React.FormEvent<HTMLFormElement>) {
    event.preventDefault();

    const form = event.currentTarget;
    const formData = new FormData(form);
    const email = formData.get("email") as string;

    setIsSubmitting(true);
    setError("");
    setSuccess(false);

    try {
      // Uses the mock subscribe() API defined above.
      const result = await subscribe(email);

      if (!result.success) {
        setError(result.error);
        return;
      }

      setSuccess(true);
      // Reset the form after a successful subscription.
      form.reset();
    } catch {
      setError("Something went wrong. Please try again.");
    } finally {
      setIsSubmitting(false);
    }
  }

  return (
    <form onSubmit={handleSubmit}>
      <input type="email" name="email" placeholder="Enter your email" required />

      <button type="submit" disabled={isSubmitting}>
        {isSubmitting ? "Subscribing..." : "Subscribe"}
      </button>

      {error && <p role="alert">{error}</p>}
      {success && <p>Successfully subscribed!</p>}
    </form>
  );
}
```

## Handling form submissions with `action`

Here is the same example written using the `action` prop:

```tsx
import { useState } from "react";
import { useFormStatus } from "react-dom";

// Track submission status to disable the button and show progress.
// We'll see why we need this component later.
function SubmitButton() {
  const { pending } = useFormStatus();

  return (
    <button type="submit" disabled={pending}>
      {pending ? "Subscribing..." : "Subscribe"}
    </button>
  );
}

// Show success or error messages, hiding them while submitting.
// We'll see why we need this component later, too.
function FormMessages({ error, success }: { error: string; success: boolean }) {
  const { pending } = useFormStatus();

  if (pending) return null;

  return (
    <>
      {error && <p role="alert">{error}</p>}
      {success && <p>Successfully subscribed!</p>}
    </>
  );
}

export default function NewsletterForm() {
  const [error, setError] = useState("");
  const [success, setSuccess] = useState(false);

  async function action(formData: FormData) {
    const email = formData.get("email") as string;

    setError("");
    setSuccess(false);

    try {
      // Uses the mock subscribe() API defined above.
      const result = await subscribe(email);

      if (!result.success) {
        setError(result.error);
        return;
      }

      setSuccess(true);
    } catch {
      setError("Something went wrong. Please try again.");
    }
  }

  return (
    <form action={action}>
      <input type="email" name="email" placeholder="Enter your email" required />

      <SubmitButton />
      <FormMessages error={error} success={success} />
    </form>
  );
}
```

## Comparing `action` prop with plain `onSubmit`

As you may notice there are some changes between the two examples. Let's go through what changes when we use `action` instead of `onSubmit`.

With `action`, we don't need `event.preventDefault()` - React handles the submission without triggering the browser's default navigation.

The action receives `FormData` directly, so we don't have to access `event.currentTarget` and construct it ourselves.

### Automatic form reset

React resets uncontrolled fields when the action completes without throwing, eliminating the manual `form.reset()` call.
In our `action` example, since we handle the error without throwing, React clears the email field even when
the subscription fails. In the `onSubmit` example, we call `form.reset()` only after a successful subscription, so the email stays in the field when something goes wrong.

It is possible to preserve form values after action as explained [here](https://react.dev/reference/react-dom/components/form#preserve-form-values-after-an-action).
The gist is that we have to save the value in state and pass it as field's `defaultValue` and update the state when the action finishes.

For more options, see React’s documentation on [other ways to control form resets](https://react.dev/reference/react-dom/components/form#other-ways-to-control-form-resets).

### Function passed to `action` runs in a Transition

Another difference from plain `onSubmit` is that React runs the function passed to `action` inside a Transition
(following the [action prop pattern](https://react.dev/reference/react/useTransition#exposing-action-props-from-components)).
This lets us use features that work with Transitions, such as optimistic updates and error boundaries.

#### `useFormStatus`, `SubmitButton`, and `FormMessages`

Notice that we also extracted the submit button and messages into `SubmitButton` and `FormMessages` so they can use [`useFormStatus`](https://react.dev/reference/react-dom/hooks/useFormStatus). `SubmitButton` disables the submit button and displays "Subscribing..." while submitting, and `FormMessages` hides previous error or success messages during submission.

State updates made synchronously inside Transitions (those before the first `await`, like `setError("")` and `setSuccess(false)` in our `action` example) are marked as Transition updates and can be deferred to prioritize more urgent updates. As a result, a manual loading flag set that way may never appear during the request, which is why we use `useFormStatus` in `SubmitButton` for the loading indicator instead. Similarly, the clearing of a previous error or success message may be deferred, leaving the old message visible even while the button displays "Subscribing...". To prevent this we use `FormMessages` that reads pending state from `useFormStatus` and hides previous messages during submission.

Just a note: `useFormStatus` reads the status of a parent `<form>`, so we call it in `SubmitButton` and `FormMessages`, which are rendered inside the form.
Calling it in `NewsletterForm` itself would not track the form that component returns.

#### Note: Updates after an async request are not Transition updates
 
When you use `await` inside a Transition, the state updates after the `await` are not marked as Transition updates. They are regular urgent updates. As [the React docs explain](https://react.dev/reference/react/useTransition#react-doesnt-treat-my-state-update-after-await-as-a-transition), you must wrap any state updates after an async request in another `startTransition` to mark them as Transitions.
 
This is, in a way, the opposite of the problems we saw in the previous section with potentially setting a loading indicator and clearing previous messages before the `await`, where those updates could be deferred until the Transition settles.

An update after the `await` is the other way around: it is urgent and renders immediately (unless wrapped in another `startTransition`). So for a moment the UI can show a mix of old and new state.
 
In our `action` example, `setError(result.error)` and `setSuccess(true)` run after `await`, so they render right away, even while the action is still pending. That's harmless here because `FormMessages` hides the messages while the action is pending, so the mix of old and new state is never visible. 

## Handling form submissions with `onSubmit` and `useTransition`

As we said `action` prop runs the function passed to it inside a Transition. However, we can also start a Transition ourselves
by combining `onSubmit` with `useTransition`. This hook returns `isPending` to track pending work and `startTransition` to start the Transition:

```tsx
import { useState, useTransition } from "react";

export default function NewsletterForm() {
  const [isPending, startTransition] = useTransition();
  const [error, setError] = useState("");
  const [success, setSuccess] = useState(false);

  function handleSubmit(event: React.FormEvent<HTMLFormElement>) {
    event.preventDefault();

    const form = event.currentTarget;
    const formData = new FormData(form);
    const email = formData.get("email") as string;

    setError("");
    setSuccess(false);

    startTransition(async () => {
      try {
        // Uses the mock subscribe() API defined above.
        const result = await subscribe(email);

        if (!result.success) {
          setError(result.error);
          return;
        }

        setSuccess(true);
        // Reset the form after a successful subscription.
        form.reset();
      } catch {
        setError("Something went wrong. Please try again.");
      }
    });
  }

  return (
    <form onSubmit={handleSubmit}>
      <input type="email" name="email" placeholder="Enter your email" required />

      <button type="submit" disabled={isPending}>
        {isPending ? "Subscribing..." : "Subscribe"}
      </button>

      {!isPending && error && <p role="alert">{error}</p>}
      {!isPending && success && <p>Successfully subscribed!</p>}
    </form>
  );
}
```

 Here we clear the previous error and success messages *before* calling `startTransition`, so they disappear immediately (unlike in the example with the `action` prop, where these updates are part of a Transition and may be deferred).
We use `isPending` for the loading indicator and don't need `useFormStatus` in this example.

The same caveat applies here: `setError(result.error)` and `setSuccess(true)` run after `await`, so they are regular urgent updates (see [Updates after `await` are not Transition updates](#note-updates-after-an-async-request-are-not-transition-updates)). This means the messages could appear while the form is still pending (while "Subscribing..." is displayed). To prevent this, we use the `!isPending` guard, just as we used `useFormStatus().pending` to hide messages in the previous example.

There is another difference now between using `action` prop and `onSubmit` with `useTransition`: progressive enhancement [when working with Server Functions](https://react.dev/reference/react-dom/components/form#handle-form-submission-with-a-server-function).
With `onSubmit`, our submission handler runs on the client, meaning JavaScript must be loaded and the component hydrated before the handler can execute.
On the other hand, when we pass a Server Function to the action prop, React can support form submissions even before JavaScript has loaded.
This is something that `onSubmit` with `useTransition` cannot provide.

## Next: `useActionState`

There is also another option of working with the forms which works with the `action` prop: [`useActionState`](https://react.dev/reference/react/useActionState).
It returns the action's result as state and exposes an `isPending` flag, so we don't need separate `useState`
calls or a `useFormStatus` child component. This is a topic maybe for another post.

## Notes

These examples use uncontrolled inputs, so their values are not stored in React state. All three approaches also work with [controlled](https://react.dev/reference/react-dom/components/input#controlling-an-input-with-a-state-variable) inputs.
With controlled inputs, we would manage the email with `value` and `onChange`, could read it from state instead of `FormData`, and would clear it
with `setEmail("")` rather than `form.reset()` or the automatic reset from `action`. Automatic resets only apply to uncontrolled fields;
the pending-state and Transition behavior discussed above stays the same.
